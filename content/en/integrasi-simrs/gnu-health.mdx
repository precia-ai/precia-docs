# GNU Health

This page explains how the integration between **GNU Health** and PRECIA works, from a hospital staff point of view. GNU Health is a hospital information system built on the Tryton framework. Staff access it through the Tryton web client (known as **sao**), so every step on this page is done in a browser, with no extra application to install.

The integration runs in two directions:

1. **From GNU Health to PRECIA.** An imaging test request raised by staff in GNU Health is sent to PRECIA and becomes one clinical transaction in the destination unit.
2. **From PRECIA to GNU Health.** Once a validating physician publishes the AI analysis result in PRECIA, a summary of that result is written back into GNU Health as a note attached to the same imaging test request.

This way staff do not have to copy patient data by hand, and the AI analysis result can be read directly from the GNU Health medical record.

Every screenshot on this page follows one real case end to end: GNU Health order `010`, imaging study `TEST008`, patient Zenon Betz, Matt (GNU Health patient ID `97234436`), destination unit **Poliklinik Kardiologi** in organization "RS Uji Coba GNU Health". Reading the PRECIA audit trail directly confirms both legs are genuinely automatic, not run by hand: the transaction was created by `actor_type=SERVICE actor_label="GNU Health dev connector"` from the docker bridge address, and once the validation was published, delivery back to GNU Health started 56 milliseconds later under `actor_type=SYSTEM actor_label=simrs-delivery-worker` — far too fast for a person to have triggered it.

## Before you start

Prepare the following:

- An active GNU Health account with access rights to the **Medical Imaging** menu.
- The address of your hospital's GNU Health web client. This address is provided by the hospital technical team or the PRECIA implementation team.
- A PRECIA account in the same organization, so you can check the incoming transaction.
- Patient records already registered in GNU Health, because the Patient field only accepts existing patients.

## 1. Checking the connection settings in PRECIA

Each organization's SIMRS connection settings are stored on the **Settings > SIMRS Integration** page in PRECIA. That page holds the connector (adapter) the organization uses and the destination endpoint URL.

![SIMRS Integration page in PRECIA, the Adapter field and the Endpoint URL field marked with a blue box](/screenshots/en/integrasi-simrs/gnu-health/01-pengaturan-koneksi.png)

Selecting **GNU Health** in the **Adapter** field updates the description text and the credential label below it to match GNU Health's own connector requirements, as shown above.

As hospital staff you do not need to fill in anything on this page yourself. Registering and saving the connection is handled by the PRECIA implementation team during onboarding. Simply confirm with that team that your organization's connection has been registered and has passed its self test before staff start creating imaging test requests.

## 2. Signing in to GNU Health

Open the GNU Health web client address in a browser. The **Login** box appears in the middle of the screen.

![GNU Health Login box, the filled-in User name field and the LOGIN button marked with a blue box](/screenshots/en/integrasi-simrs/gnu-health/02-halaman-masuk.png)

Fill the **User name** field with your user name, then click **LOGIN**.

The **Database** field above it is already filled in with the hospital database name. Leave that field as it is and do not change it.

GNU Health then shows a second box asking for your password.

![GNU Health password entry box, the password field marked with a blue box](/screenshots/en/integrasi-simrs/gnu-health/03-kata-sandi.png)

Type your password, then click **OK** or press Enter. Once accepted, the GNU Health main screen opens with the tree menu on the left.

## 3. Raising an imaging test request

### Step 4: Open the Medical Imaging menu

In the tree menu on the left, open **Health**, then **Medical Imaging**. The branch offers two relevant entries: **Request Imaging Test**, a wizard for raising a new request, and **Imaging Test Request**, the list of requests already on file.

**Screenshot not yet available.** The account used to capture this section does not yet have the Medical Imaging module enabled; see [Current limitations](#current-limitations). An earlier screenshot of this step existed but was taken with a full administrator account rather than the account used for the rest of this page, so it is not shown here rather than mixing two different identities across one walkthrough.

To open a menu row, double click on its label. The small arrow to the left of a row expands or collapses that branch of the menu.

### Step 5: Fill in the request wizard

Double click **Request Imaging Test** to open the wizard.

**Screenshot not yet available.** The account used to capture this section does not yet have the Medical Imaging module enabled; see [Current limitations](#current-limitations). Fill in the following:

1. **Patient**: the patient name. This field is an autocomplete. Type part of the name, wait for the suggestion list to appear, then click the patient name in that list. A value that is only typed and never picked from the list will not be saved.
2. **Tests**: tick the row for the examination type that matches the AI module to be used, for example **PRECIA AI ECG** for ejection fraction analysis.

Click **REQUEST** to submit. Unlike an old draft-only form, this wizard creates the request directly in the **Requested** state, ready for the imaging unit to act on. Note the **Order** number GNU Health assigns; it is what later shows up on the PRECIA case.

### Step 6: Confirm the request on file

Open **Imaging Test Request** from the tree menu, then switch to the **All** tab, since a request that has moved past Draft no longer shows under the default tab. Order `010` is the request that has already completed its full cycle in the walkthrough this page follows.

**Screenshot not yet available**, same reason as Step 5.

## 4. Confirming the completed examination

### Step 7: Check the imaging result

Once the imaging unit performs the study and records a result, that result appears under **Imaging Test Result**, a separate list from the request itself.

**Screenshot not yet available**, same reason as Step 5.

This is the file the PRECIA connector picks up for AI analysis; the request and its result are two different records linked by the same order number.

## 5. Finding the case in PRECIA

### Step 8: Open the unit worklist

The PRECIA connector reads new requests from GNU Health and creates one clinical transaction in the destination unit. Sign in to PRECIA, open the **Clinical** menu, then in the **Transaction Worklist** card pick the destination unit in the **Unit** filter, **Poliklinik Kardiologi** in this example.

![Clinical Workflows page in PRECIA, the Unit filter and the transaction row for GNUHEALTH-10 marked with a blue box](/screenshots/en/integrasi-simrs/gnu-health/08-daftar-kerja-precia.png)

A transaction that came from GNU Health can be recognized by its **Code**, in the form `GNUHEALTH-<sequence number>`, for example `GNUHEALTH-10`.

### Step 9: Open the case detail

Click the transaction row to open the detail page.

![Transaction detail page in PRECIA, the transaction code and the Poliklinik Kardiologi unit marked with a blue box](/screenshots/en/integrasi-simrs/gnu-health/09-detail-transaksi-precia.png)

The **Notes** section carries the raw GNU Health context, including the imaging study code and the order number, for example "GNU Health imaging study TEST008 (PRECIA AI ECG Ejection Fraction), request 010". A GNU Health imaging test request carries no file attachment on its own; the source image is added on the PRECIA side once the case arrives, exactly as shown in Step 10.

## 6. Watching the AI module process the case

### Step 10: Open the AI module tab

On the same case detail page, click the AI module tab, **ECG EF Screening** in this example. It shows the source file uploaded for analysis and the module's processing status.

![PRECIA case detail, ECG EF Screening tab, the uploaded source file and the Completed status marked with a blue box](/screenshots/en/integrasi-simrs/gnu-health/10-slot-ai-terisi.png)

The case example this page follows has already been processed, so its status reads **Completed**. A case appearing in PRECIA does not run AI analysis on its own, though: an operator still needs to press the AI processing button once a file is uploaded, the same limitation documented for every SIMRS on this site.

### Step 11: Read the AI result

Once processing finishes, the same tab shows the AI module's output.

![PRECIA case detail, ECG EF Screening tab showing the confidence score and classification marked with a blue box](/screenshots/en/integrasi-simrs/gnu-health/11-hasil-ai-tampil.png)

This result, together with the source file, is what a validating physician reviews next.

## 7. Publishing the validation

### Step 12: Check the published validation

Open **Validation** in the sidebar. The case for transaction `GNUHEALTH-10` shows a recorded decision with status **Published**.

![PRECIA Validation page, the row for transaction GNUHEALTH-10 marked with a blue box, the Published status marked with a blue box](/screenshots/en/integrasi-simrs/gnu-health/12-validasi-diterbitkan.png)

Publishing a validation is the trigger for the write-back leg: PRECIA sends the result to GNU Health as soon as the decision is published, without anyone running a separate step.

## 8. Reading the AI result back in GNU Health

### Step 13: Reopen the completed order

Back in GNU Health, open **Imaging Test Request**, switch to the **All** tab, and open order `010` again. The **State** field now reads **Done**, and the note button on the toolbar shows a note is attached.

**Screenshot not yet available.** The account used to capture this section does not yet have the Medical Imaging module enabled; see [Current limitations](#current-limitations).

### Step 14: Open the AI result note

Click the Notes button, then double click the note row to open its contents. The note is authored by the PRECIA integration account rather than a member of staff, and holds the AI module name, the confidence level, the validation status, and a summary of the result. Click **OK** to close the note box; it stays attached to the imaging test request and can be reopened at any time.

**Screenshot not yet available**, same reason as Step 13.

## Current limitations

The GNU Health integration is still at trial stage. The following limitations apply and should be understood before it is used in day-to-day work.

1. **Steps 4 through 7 and 13 through 14 have no screenshot yet.** The demo account used to capture that half of this page can log in, but its role does not yet include the Medical Imaging module (confirmed live: the full expanded Health menu for this account has no Medical Imaging entry). Access has been requested; no fixed date yet. The written description of those steps reflects GNU Health's documented Request Imaging Test / Imaging Test Request flow, but has not been re-verified against the live screen in this pass.
2. **The AI module still has to be triggered by hand.** See Step 10; a case appearing in PRECIA does not analyse itself. Both the request delivery from GNU Health and the result delivery back to it, by contrast, are confirmed automatic from the platform's own audit trail.
3. **A GNU Health imaging test request carries no attachment.** The Imaging Test Request wizard offers neither a file attachment nor a DICOM image reference. The source file for AI analysis is uploaded on the transaction detail page in PRECIA, as shown in Step 10.
4. **AI modules must be configured on the destination unit first.** Until the unit AI policy is set, the AI Modules panel on the detail page reports that no slots are configured, and the transaction stops at the Unprocessed status.
5. **The AI result is written back as a note, not as a structured examination result.** The result summary appears in the Notes box of the imaging test request, not under the Imaging Test Result menu.
